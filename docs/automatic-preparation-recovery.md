# 自动启动与恢复检查：1.6.16-test.3

基线：测试分支 `1913e36`（1.6.16-test.2），保留该版本任务登记修复。用户报告的是 1.6.14：正文结束后出现“这条还没有兔子镜”的失败卡，手动重说才会生成，偶尔整页无响应。

## 已复现的问题

正文已经结束并获得自动生成授权，但宿主在发送副 API 之前又改写正文时，排队中的任务需要重新确认最终正文。此时一次被动界面同步可能先运行：它只看到没有成品、没有已发送请求，便补失败卡并写入 `missing-external-shell` 停止标记。接下来的正文确认又拒绝刷新已有失败标记的任务，于是自动启动被自身恢复流程阻断。手动重说清除该标记，故能继续生成。

这是已确认的一条代码路径，不代表所有“生成失败”都由它造成。截图的文字是恢复流程的通用提示，不是接口返回的真实错误原因。

## 变更范围

- `src/independentApi/earlyBody.js` 检查当前聊天、楼层是否仍有未取消的生成 poll。普通同步、旧错误壳重新挂载均不能把这类等待中的任务标为缺壳失败，并保留或补回 loading 占位。
- `src/independentApi/missingRetryShell.js` 的恢复判定纳入“已有排队中的生成任务”。它只决定是否补失败卡，不赋予发送权限、不创建任务。
- 发送仍经过原有 poll 的聊天、正文、操作身份、真实失败和请求租约检查。取消、历史缺失、其他聊天或其他楼层的任务不会被当成本楼层的活任务。
- 同一恢复路径的被动视口缓存增加完整、可见的 error 卡。缓存比较加入状态、记录键、正文指纹和错误操作节点；loading、缺失操作按钮、隐藏卡仍需检查。显式宿主事件、手动操作和结构替换恢复路径保持不变。
- 其他运行文件只同步缓存标识，避免旧模块混用。不改 Prompt、模型参数、抽签、自动重试次数、等待时限或保存格式，不清理用户成品。

## 回归证据

新增 `tests/automaticPreparationRecovery.test.mjs`，执行真实同步、补卡、授权刷新和生成 poll 函数，使用确定时钟以及 DOM/发送边界模拟，不调用真实模型。

- 生产代码修改前，三个竞态用例失败：普通同步、重新挂载、旧 error 壳会写入停止标记；修复后均通过，并验证稳定后的同一任务只到达发送入口一次。
- 覆盖任务取消、跨聊天/楼层、正文对象或操作被替换、真实失败保留、loading 外壳缺失后恢复。
- 被动恢复的 100 次模拟交互，在未修复时同步次数为 101，修复后为 1（首次检查）。正文、swipe、身份、状态和错误按钮节点变化仍使缓存失效。按钮被删用例验证触发重同步，按钮重建本身是 DOM 边界模拟。
- 新增 15 项、相邻既有 16 项，共 31 项通过。独立复核同组通过。
- 全套 390 项：355 通过、28 失败、7 跳过；test.2 基线 375 项：340 通过、28 失败、7 跳过。失败名称逐项相同，没有新增失败，不能称全套通过。

## 验收边界

更新测试分支后完整刷新或重启宿主，确认 manifest 为 1.6.16-test.3。无需清缓存数据、删除聊天或重新导入母本。

对反复同步的修复证明减少了本地重复工作，不是实际手机性能基准。用户整页卡死的唯一根因尚未确认，也未在真实手机、宿主和服务商连接中完成验收。仍卡住时需要复现期间的宿主性能报告，不能把未知卡死都归为本次已修复。
